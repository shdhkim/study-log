# Oracle SQL 권한 관리 정리

> 범위: 사용자·스키마·테이블스페이스, 시스템 권한, 객체 권한, 스키마 권한(26ai), ROLE, GRANT/REVOKE, 권한 조회  
> 기준: Oracle Database 19c/21c와 Oracle AI Database 26ai의 차이를 명시  
> 예제 계정: `A`(테이블 소유자), `B`·`C`(일반 사용자), `SYSTEM`(관리 계정)

## 1. 먼저 전체 구조 이해하기

- **사용자(USER)**: DB에 로그인하는 계정. 예: `A`, `B`, `SYSTEM`.
- **스키마(SCHEMA)**: 사용자가 소유한 테이블·뷰·인덱스 등 객체의 논리적 묶음. 일반적으로 사용자 `A`의 스키마 이름도 `A`다.
- **테이블스페이스(TABLESPACE)**: 테이블·인덱스 등의 데이터를 저장할 논리적 저장 공간. 스키마와 일대일 관계가 아니다.
- **권한(PRIVILEGE)**: 어떤 SQL 작업을 수행할 수 있는지 정하는 허가.
- **ROLE**: 여러 권한(그리고 다른 ROLE)을 묶어 사용자에게 할당하는 그룹.

```text
사용자 A ── 소유 ──> A 스키마 ── 포함 ──> A.EMPLOYEE, A.DEPARTMENT
                                          │
                              실제 세그먼트는 테이블스페이스에 저장

관리자 ── GRANT 권한 ──> ROLE ── GRANT ROLE ──> 사용자 B
```

### 스키마와 테이블스페이스는 별개

- 스키마 `A`의 테이블 여러 개가 서로 다른 테이블스페이스에 저장될 수 있다.
- 여러 스키마의 테이블이 같은 `USERS` 테이블스페이스를 사용할 수도 있다.
- `SYSTEM`은 관리자 **사용자명**이면서 `SYSTEM`이라는 **시스템용 테이블스페이스 이름**이기도 하다. 이름이 같아도 개념이 다르다.
- 테이블 생성에는 `CREATE TABLE`과 해당 테이블스페이스의 **QUOTA(할당량)** 또는 `UNLIMITED TABLESPACE` 등 적절한 저장공간 권한이 필요하다.

```sql
-- 관리자: 사용자 생성과 기본 테이블스페이스 지정
CREATE USER A IDENTIFIED BY "Example_Strong_Password_1"
  DEFAULT TABLESPACE USERS
  QUOTA 100M ON USERS;

GRANT CREATE SESSION, CREATE TABLE TO A;

-- 기존 사용자의 기본 테이블스페이스 변경
ALTER USER A DEFAULT TABLESPACE USERS;

-- 테이블스페이스 할당량 부여
ALTER USER A QUOTA 200M ON USERS;

-- 현재 사용자별 기본 테이블스페이스 확인(조회 권한 필요)
SELECT USERNAME, DEFAULT_TABLESPACE
FROM DBA_USERS
WHERE USERNAME = 'A';

-- 테이블이 사용하는 테이블스페이스 확인
SELECT OWNER, TABLE_NAME, TABLESPACE_NAME
FROM DBA_TABLES
WHERE OWNER = 'A';
```

## 2. DDL·DML·DCL과 권한

| 분류             | 대표 명령                     | 의미                |
| ---------------- | ----------------------------- | ------------------- |
| DDL              | CREATE, ALTER, DROP, TRUNCATE | 객체 정의·구조 변경 |
| DML              | INSERT, UPDATE, DELETE, MERGE | 데이터 변경         |
| DQL(관용적 분류) | SELECT                        | 데이터 조회         |
| DCL              | GRANT, REVOKE                 | 권한 부여·회수      |
| TCL              | COMMIT, ROLLBACK, SAVEPOINT   | 트랜잭션 관리       |

**중요:** DDL인지 DML인지와 별개로 필요한 권한 종류가 결정된다. 예를 들어 `ALTER`는 개별 테이블 객체 권한으로 줄 수 있지만 `DROP`은 그렇게 할 수 없다.

## 3. 권한 3종류 비교

| 구분        | 적용 범위                                   | 예시                               | 주의                                              |
| ----------- | ------------------------------------------- | ---------------------------------- | ------------------------------------------------- |
| 시스템 권한 | DB 전반 또는 자신의 스키마에 관한 특정 작업 | `CREATE TABLE`, `SELECT ANY TABLE` | `ANY`는 다른 스키마까지 넓게 허용하는 경우가 많음 |
| 객체 권한   | 특정 테이블·뷰 등                           | `SELECT ON A.EMPLOYEE`             | 소유자가 직접 부여 가능                           |
| 스키마 권한 | 지정한 스키마 전체                          | `SELECT ANY TABLE ON SCHEMA A`     | **26ai부터 지원**                                 |

### 3-1. 시스템 권한

```sql
GRANT CREATE SESSION TO B;
GRANT CREATE TABLE TO B;        -- 기본적으로 B 자신의 스키마에 생성
GRANT CREATE ANY TABLE TO B;    -- 일반적으로 다른 스키마에도 테이블 생성
GRANT SELECT ANY TABLE TO B;    -- 광범위하게 다른 스키마 테이블 조회
GRANT ALTER ANY TABLE TO B;
GRANT DROP ANY TABLE TO B;
```

`ANY`는 권한 이름의 일부다. 모든 권한이 단순히 `ANY`를 제거한 짝을 갖는 것은 아니다. 예를 들어 `SELECT TABLE`, `DROP TABLE`을 독립된 시스템 권한이라고 생각하면 안 된다. `SELECT ANY TABLE` 등에는 `SYS`·`AUDSYS` 객체 같은 제한도 있다.

### 3-2. 개별 테이블 객체 권한

```sql
-- A 테이블 소유자 또는 적법한 부여권자가 실행
GRANT SELECT ON A.EMPLOYEE TO B;
GRANT INSERT, UPDATE, DELETE ON A.EMPLOYEE TO B;
GRANT ALTER ON A.EMPLOYEE TO B;

-- 특정 테이블에 '부여 가능한 객체 권한'을 한번에 부여
GRANT ALL PRIVILEGES ON A.EMPLOYEE TO B;
```

**지원되지 않는 문법:**

```sql
GRANT DROP ON A.EMPLOYEE TO B;       -- 불가능
GRANT TRUNCATE ON A.EMPLOYEE TO B;   -- 불가능
```

`GRANT ALL PRIVILEGES ON A.EMPLOYEE` 역시 `DROP`/`TRUNCATE` 권한을 만들어주지 않는다.

### 3-3. DROP과 TRUNCATE

```sql
GRANT DELETE ON A.EMPLOYEE TO B;  -- 행 단위 DELETE 가능
-- 위 권한으로 TRUNCATE TABLE A.EMPLOYEE 실행은 불가

GRANT DROP ANY TABLE TO B;        -- 보통 타 스키마 테이블 DROP 및 TRUNCATE 허용
```

- `DELETE`는 DML이며 조건절과 트랜잭션 롤백이 가능하다.
- `TRUNCATE`는 DDL이며 전체 행을 신속히 제거하고 일반적인 DML처럼 롤백하지 않는다.
- `DROP`은 테이블 자체를 제거한다.
- 특정 테이블 하나만 TRUNCATE하도록 허용해야 한다면, 소유자가 정의한 `AUTHID DEFINER` 프로시저로 허용 작업을 제한하는 방식을 고려한다. 무작정 `DROP ANY TABLE`을 주면 위험하다.

## 4. 특정 스키마 전체에 권한을 부여할 수 있나?

**버전이 핵심이다. Oracle 공식 릴리스 문서에 따르면 스키마 권한은 Oracle AI Database 26ai부터 도입되었다.** 19c/21c/23ai에는 아래 `ON SCHEMA` 구문을 사용하지 않는다.

### 4-1. 26ai: 스키마 권한

```sql
-- 적절한 권한을 가진 사용자 또는 A 스키마 소유자가 실행
GRANT SELECT ANY TABLE ON SCHEMA A TO B;
GRANT ALTER ANY TABLE ON SCHEMA A TO B;
GRANT CREATE ANY TABLE ON SCHEMA A TO B;
GRANT DROP ANY TABLE ON SCHEMA A TO B;
```

- 같은 이름의 시스템 권한에 비해 적용 범위를 **A 스키마로 제한**한다.
- A 스키마에 현재 존재하는 객체와 **나중에 생성되는 객체**에도 적용된다.
- `DROP ANY TABLE ON SCHEMA A`는 이 스키마 범위 안에서 DROP/TRUNCATE 작업에 사용된다.
- 시스템 권한이나 다른 ROLE을 통해 별도 권한을 받았다면 A 외의 스키마에도 접근할 수 있다.
- `SYS` 스키마에는 스키마 권한을 부여할 수 없다.

```sql
-- A 스키마에 지원되는 모든 스키마 권한 (26ai)
GRANT ALL PRIVILEGES ON SCHEMA A TO B;
```

여기서 `ALL PRIVILEGES`는 **지원되는 스키마 권한 전체**를 말한다. 데이터베이스의 모든 관리자 권한을 뜻하는 것은 아니다.

### 4-2. 19c/21c/23ai: 스키마 단위 GRANT 불가

```sql
-- 개별 객체 권한은 테이블마다 부여 가능
GRANT SELECT, UPDATE, ALTER ON A.EMPLOYEE TO B;
GRANT SELECT, UPDATE, ALTER ON A.DEPARTMENT TO B;
```

여러 테이블에 반복 GRANT할 수는 있지만 **새로 생성되는 테이블에 자동 적용되지 않는다.** 그리고 `DROP`·`TRUNCATE`를 테이블별 객체 권한으로 바꿔 줄 수도 없다. 실무 대안은 신규 객체 생성 시 권한 부여 자동화, 제한된 소유자 프로시저, 필요한 작업에 국한된 설계 등이다.

## 5. 누가 권한을 부여할 수 있나?

| 권한 종류         | 대표적인 부여 자격                                                                                       | 권한을 받은 사람이 재부여하려면 |
| ----------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------- |
| 시스템 권한       | `GRANT ANY PRIVILEGE`, 해당 시스템 권한의 `ADMIN OPTION` 보유자                                          | `WITH ADMIN OPTION`             |
| 테이블 객체 권한  | 객체 소유자, `GRANT OPTION` 보유자, `GRANT ANY OBJECT PRIVILEGE` 보유자                                  | `WITH GRANT OPTION`             |
| 스키마 권한(26ai) | 스키마 소유자, 해당 권한의 `ADMIN OPTION` 보유자, `GRANT ANY SCHEMA PRIVILEGE` 등 적절한 부여권한 보유자 | `WITH ADMIN OPTION`             |
| ROLE              | ROLE 관리 권한 또는 해당 ROLE의 `ADMIN OPTION` 보유자                                                    | `WITH ADMIN OPTION`             |

### SYSTEM은 모든 권한을 갖나?

- `SYSTEM`은 일반적으로 DBA 역할을 가진 강력한 관리 계정이므로 많은 권한을 부여할 수 있다.
- 그렇다고 **무조건 모든 권한을 가진 것**은 아니다. 실제 권한·활성 ROLE·데이터 딕셔너리 보호·관리자 권한·컨테이너 범위를 확인해야 한다.
- `SYS`는 데이터 딕셔너리 등을 소유하는 특수 계정이며 `SYSDBA`는 일반적인 시스템 권한/ROLE과 다른 **관리 권한**이다.
- 일반 업무에서 `SYS`/`SYSTEM`을 애플리케이션 계정처럼 사용하지 않는다.

```sql
-- SYSTEM 등 권한을 가진 관리자가 실행
GRANT SELECT ANY TABLE TO B;
GRANT SELECT ON A.EMPLOYEE TO B;
```

## 6. 받은 권한을 다른 사람에게 다시 줄 수 있나?

### 6-1. 시스템 권한: WITH ADMIN OPTION

```sql
GRANT SELECT ANY TABLE TO B WITH ADMIN OPTION;
-- B가 C에게 같은 시스템 권한을 부여
GRANT SELECT ANY TABLE TO C;
```

### 6-2. 객체 권한: WITH GRANT OPTION

```sql
-- A가 B에게
GRANT SELECT, UPDATE ON A.EMPLOYEE TO B WITH GRANT OPTION;

-- B가 C에게 (받은 범위 내)
GRANT SELECT ON A.EMPLOYEE TO C;
```

`WITH GRANT OPTION` 없이 받았다면 B는 조회할 수 있어도 다른 사람에게 해당 권한을 부여할 수 없다. **객체 권한을 ROLE에 부여하면서 `WITH GRANT OPTION`을 붙이는 것은 지원되지 않는다.**

### 6-3. 스키마 권한: WITH ADMIN OPTION (26ai)

```sql
GRANT SELECT ANY TABLE ON SCHEMA A TO B WITH ADMIN OPTION;
-- B가 C에게
GRANT SELECT ANY TABLE ON SCHEMA A TO C;
```

### 6-4. 회수의 차이

```sql
REVOKE SELECT ON A.EMPLOYEE FROM B;
REVOKE SELECT ANY TABLE FROM B;
REVOKE SELECT ANY TABLE ON SCHEMA A FROM B; -- 26ai
```

- **객체 권한**은 B를 통해 C에게 전달되었다면, B 권한 회수에 따라 C의 전달 권한도 연쇄 회수될 수 있다(다른 독립 경로로 부여받았다면 남을 수 있음).
- **시스템 권한**을 `ADMIN OPTION`으로 부여했다가 B로부터 회수해도 B가 C에게 이미 부여한 권한은 일반적으로 자동 회수되지 않는다.

## 7. ROLE은 무엇인가?

ROLE은 여러 권한을 담는 그룹이다. 사용자마다 테이블별 GRANT를 반복하지 않아도 된다.

```text
HR_MANAGER (ROLE)
 ├─ SELECT, UPDATE ON A.EMPLOYEE
 ├─ SELECT ON A.DEPARTMENT
 └─ CREATE SESSION
       ↓ GRANT HR_MANAGER
    사용자 B, C, D
```

### 7-1. ROLE 생성 후 객체 권한·시스템 권한 부여

```sql
CREATE ROLE HR_MANAGER;

GRANT SELECT, UPDATE ON A.EMPLOYEE TO HR_MANAGER;
GRANT SELECT ON A.DEPARTMENT TO HR_MANAGER;
GRANT CREATE SESSION TO HR_MANAGER;

GRANT HR_MANAGER TO B;
GRANT HR_MANAGER TO C;
```

### 7-2. ANY 시스템 권한도 ROLE에 부여 가능

```sql
CREATE ROLE DATA_ADMIN_ROLE;
GRANT SELECT ANY TABLE TO DATA_ADMIN_ROLE;
GRANT ALTER ANY TABLE TO DATA_ADMIN_ROLE;
GRANT CREATE ANY TABLE TO DATA_ADMIN_ROLE;
GRANT DROP ANY TABLE TO DATA_ADMIN_ROLE;
GRANT DATA_ADMIN_ROLE TO B;
```

이 ROLE은 범위가 매우 넓으므로 운영 계정에 부여할 때 주의한다.

### 7-3. 스키마 권한도 ROLE에 부여 가능 (26ai)

```sql
CREATE ROLE A_SCHEMA_MANAGER;
GRANT SELECT ANY TABLE ON SCHEMA A TO A_SCHEMA_MANAGER;
GRANT ALTER ANY TABLE ON SCHEMA A TO A_SCHEMA_MANAGER;
GRANT DROP ANY TABLE ON SCHEMA A TO A_SCHEMA_MANAGER;
GRANT A_SCHEMA_MANAGER TO B;
```

### 7-4. ROLE 자체를 재부여

```sql
GRANT HR_MANAGER TO B WITH ADMIN OPTION;
-- B가 역할 자체를 C에게 부여
GRANT HR_MANAGER TO C;
```

**중요:** B가 ROLE을 다른 사람에게 부여할 수 있는 것과, ROLE에 담긴 `SELECT ANY TABLE` 등을 개별적으로 C에게 GRANT할 수 있는 것은 다르다. ROLE의 권한이 곧 B에게 `ADMIN OPTION`으로 직접 부여된 권한이 되는 것은 아니다.

### 7-5. ROLE의 제약

- ROLE은 **활성화**되어 있어야 그 권한을 사용할 수 있다.
- 일반적인 `AUTHID DEFINER` 저장 프로시저에서는 ROLE을 통한 권한이 비활성화되므로, 필요한 권한을 프로시저 소유자에게 직접 부여해야 하는 경우가 많다.
- 다른 ROLE을 포함할 수도 있다.
- `SYSDBA` 같은 관리자 권한은 일반 ROLE 권한과 별개다.
- 모든 시스템 권한이 ROLE에 부여 가능한 것은 아니다(예: `UNLIMITED TABLESPACE` 제한).

## 8. ANY 권한을 헷갈리지 않기

| SQL                                       | 적용 범위 / 의미                                 |
| ----------------------------------------- | ------------------------------------------------ |
| `GRANT CREATE TABLE TO B`                 | B 자신의 스키마에 테이블 생성                    |
| `GRANT CREATE ANY TABLE TO B`             | 다른 일반 사용자 스키마에도 테이블 생성 가능     |
| `GRANT SELECT ON A.EMPLOYEE TO B`         | A.EMPLOYEE 하나만 SELECT                         |
| `GRANT SELECT ANY TABLE TO B`             | DB의 폭넓은 대상에 SELECT                        |
| `GRANT SELECT ANY TABLE ON SCHEMA A TO B` | A 스키마만 SELECT(26ai)                          |
| `GRANT DROP ANY TABLE TO B`               | 다른 스키마 테이블 DROP/TRUNCATE까지 폭넓게 허용 |
| `GRANT DROP ANY TABLE ON SCHEMA A TO B`   | A 스키마 범위에 제한(26ai)                       |

**`ANY`는 권한 이름에 포함되는 문구이며, `ON SCHEMA A`를 붙이면 그 권한의 대상 범위를 특정 스키마로 좁힐 수 있다(26ai).**

## 9. 권한 조회 SQL (실무에서 중요)

관리자용 `DBA_*` 뷰는 조회 권한이 필요하다. 객체 **소유자 자체의 기본 권한**은 다른 사람에게 부여받은 GRANT 기록과 다르므로 모든 권한을 GRANT 내역 하나만으로 계산하면 안 된다. ROLE 상속도 함께 확인해야 한다.

### 9-1. DB 버전 확인

```sql
SELECT BANNER FROM V$VERSION;
-- 해당 뷰 조회 권한이 없다면 DBA에게 버전 문의
```

### 9-2. 사용자 A에게 직접 부여한 시스템 권한

```sql
SELECT GRANTEE, PRIVILEGE, ADMIN_OPTION
FROM DBA_SYS_PRIVS
WHERE GRANTEE = 'A'
ORDER BY PRIVILEGE;
```

### 9-3. 사용자 A에게 부여한 테이블 객체 권한

```sql
SELECT GRANTEE, OWNER, TABLE_NAME, PRIVILEGE, GRANTABLE
FROM DBA_TAB_PRIVS
WHERE GRANTEE = 'A'
ORDER BY OWNER, TABLE_NAME, PRIVILEGE;
```

### 9-4. 반대로 A 스키마 소유 테이블을 누가 접근할 수 있나? (직접 GRANT)

```sql
SELECT OWNER, TABLE_NAME, GRANTEE, PRIVILEGE, GRANTABLE
FROM DBA_TAB_PRIVS
WHERE OWNER = 'A'
ORDER BY TABLE_NAME, GRANTEE;
```

여기에는 ROLE에게 부여한 항목도 있을 수 있다. 실제 각 사용자의 접근 경로는 ROLE 부여 관계까지 살펴야 한다.

### 9-5. A에게 부여된 ROLE

```sql
SELECT GRANTEE, GRANTED_ROLE, ADMIN_OPTION, DEFAULT_ROLE
FROM DBA_ROLE_PRIVS
WHERE GRANTEE = 'A';
```

### 9-6. ROLE 내부의 권한

```sql
SELECT ROLE, PRIVILEGE, ADMIN_OPTION
FROM ROLE_SYS_PRIVS
WHERE ROLE = 'HR_MANAGER';

SELECT ROLE, OWNER, TABLE_NAME, PRIVILEGE
FROM ROLE_TAB_PRIVS
WHERE ROLE = 'HR_MANAGER';
```

### 9-7. 현재 세션에서 사용 중인 ROLE·시스템 권한

```sql
SELECT * FROM SESSION_ROLES;
SELECT * FROM SESSION_PRIVS;
SELECT * FROM USER_ROLE_PRIVS;
```

### 9-8. 스키마 권한 조회 (26ai)

```sql
-- A가 받은 스키마 권한
SELECT GRANTEE, SCHEMA, PRIVILEGE, ADMIN_OPTION
FROM DBA_SCHEMA_PRIVS
WHERE GRANTEE = 'A';

-- A 스키마에 대해 누구에게 권한을 주었는지
SELECT GRANTEE, SCHEMA, PRIVILEGE, ADMIN_OPTION
FROM DBA_SCHEMA_PRIVS
WHERE SCHEMA = 'A';

-- 특정 ROLE이 받은 스키마 권한
SELECT ROLE, SCHEMA, PRIVILEGE, ADMIN_OPTION
FROM ROLE_SCHEMA_PRIVS
WHERE ROLE = 'A_SCHEMA_MANAGER';
```

26ai에서는 `USER_SCHEMA_PRIVS`, `SESSION_SCHEMA_PRIVS` 등도 지원한다. 19c 등에서 위 26ai 전용 뷰를 조회하면 존재하지 않을 수 있다.

## 10. 권한 회수와 ROLE 관리

```sql
-- 직접 부여한 객체 권한 회수
REVOKE UPDATE ON A.EMPLOYEE FROM B;

-- 시스템 권한 회수
REVOKE SELECT ANY TABLE FROM B;

-- ROLE 회수
REVOKE HR_MANAGER FROM B;

-- ROLE에서 객체 권한 제거: 그 ROLE에 의존하는 사용자 접근도 영향받음
REVOKE UPDATE ON A.EMPLOYEE FROM HR_MANAGER;

-- 26ai: 스키마 권한 회수
REVOKE SELECT ANY TABLE ON SCHEMA A FROM B;
```

## 11. 실무 설계 시 권장 패턴

1. **최소 권한 원칙**: 조회만 필요한 사용자에게 `DROP ANY TABLE`을 주지 않는다.
2. **여러 사용자에게 동일한 권한**: ROLE에 권한을 묶어서 부여한다.
3. **한 테이블만 접근**: 객체 권한 사용.
4. **26ai에서 특정 스키마 전체 접근**: `ON SCHEMA` 권한을 우선 고려.
5. **19c에서 특정 스키마 전체 접근**: 객체별 GRANT + 신규 테이블에 대한 자동화 전략.
6. **재부여 필요성 검토**: 사용자에게 무조건 `ADMIN OPTION` 또는 `GRANT OPTION`을 주지 않는다.
7. **저장 프로시저**: ROLE 권한에만 의존하지 말고 실행 주체·`AUTHID`·직접 부여 권한을 점검한다.
8. **관리 계정 사용 최소화**: SYS/SYSTEM 대신 목적별 운영 계정 사용.

## 12. 자주 묻는 질문 Q&A

**Q. 자신의 스키마에는 CREATE TABLE 권한이 원래 있나?**  
A. 아니다. 소유자라는 이유만으로 테이블 생성 시스템 권한이 자동 부여되지는 않는다. `CREATE TABLE` 등 필요한 권한과 테이블스페이스 할당량이 있어야 한다.

**Q. A 스키마의 모든 테이블에 B가 접근하도록 만들 수 있나?**  
A. 26ai에서는 스키마 권한을 줄 수 있다. 19c 등에서는 개별 객체 권한으로 처리하거나 별도의 제어된 설계를 고려한다.

**Q. 테이블 하나에 DROP 권한만 GRANT할 수 있나?**  
A. `GRANT DROP ON A.EMPLOYEE` 같은 테이블 객체 권한은 없다. `TRUNCATE`도 마찬가지다.

**Q. `GRANT ALL PRIVILEGES ON A.EMPLOYEE`는 DROP까지 포함하나?**  
A. 아니다. 부여 가능한 테이블 객체 권한만 포함한다.

**Q. ROLE을 받은 B가 안에 든 모든 권한을 C에게 재부여할 수 있나?**  
A. 아니다. ROLE 자체를 재부여하려면 해당 ROLE의 `ADMIN OPTION` 등이 필요하며, 내부 권한 각각을 재부여할 자격이 자동 생기는 것은 아니다.

**Q. SYSTEM이면 모든 권한을 아무 조건 없이 부여할 수 있나?**  
A. 아니다. 기본적으로 매우 강력하지만 실제 부여권한, 관리자 권한, 보호 대상, PDB/CDB 범위 등에 따른 제약이 있다.

**Q. 기존 테이블에 GRANT했으면 앞으로 만드는 테이블도 자동인가?**  
A. 개별 객체 GRANT라면 자동이 아니다. 26ai 스키마 권한은 이후 생성 객체도 적용된다.

| 시스템 권한 재부여 허용            | `WITH ADMIN OPTION`                              |
| 스키마 권한 재부여 허용            | `WITH ADMIN OPTION` (26ai)                       |
