# Oracle SQL 권한·스키마·테이블스페이스 완전 정리

> 대상: Oracle XE / XEPDB1 + DBeaver 입문·실무 학습용  
> 예시 사용자: `SYSTEM`(관리자), `APP_USER`(테이블 소유자), `TEST_USER`(접근 사용자)  
> **주의:** 예시의 비밀번호와 사용자명은 실제 환경에 맞춰 변경하고, 운영 DB에서 광범위한 `ANY` 권한을 시험 삼아 부여하지 않는다.

## 0. 요약

- **사용자(User)**: Oracle에 로그인하는 계정. 사용자를 만들면 같은 이름의 **스키마(Schema)**가 연결된다.
- **스키마**: 그 사용자가 소유하는 테이블·뷰·인덱스 같은 객체의 이름 공간. `APP_USER.EMPLOYEE`는 APP_USER 소유의 EMPLOYEE 테이블이다.
- **테이블스페이스(Tablespace)**: 테이블·인덱스 등의 저장 공간을 논리적으로 관리하는 단위. `USERS`는 흔히 사용하는 테이블스페이스 **이름**이다.
- **DEFAULT TABLESPACE**: 별도로 저장 위치를 지정하지 않았을 때의 기본값. **사용 허가가 아님**.
- **QUOTA**: 해당 테이블스페이스에 객체가 사용할 공간을 할당받을 수 있는 한도.
- **시스템 권한**: `CREATE SESSION`, `CREATE TABLE`, `CREATE ANY TABLE`처럼 **무슨 작업을 할 수 있는지** 정한다.
- **객체 권한**: `SELECT ON APP_USER.EMPLOYEE`처럼 **어느 객체에 무엇을 할 수 있는지** 정한다.
- **GRANT / REVOKE**: 권한을 주거나 회수한다.

**테이블 생성에 관한 기본 공식:** `CREATE TABLE` 시스템 권한 + 저장할 테이블스페이스에 필요한 QUOTA(또는 해당 공간 제한의 면제 조건). 계정 생성만으로 자동 충족되지 않는다.

## 1. DDL / DML / DCL / TCL은 무엇인가?

| 분류 | 뜻              | 주요 SQL                                        | 설명                                |
| ---- | --------------- | ----------------------------------------------- | ----------------------------------- |
| DDL  | 데이터 정의어   | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME` | 객체 구조 생성·변경·제거            |
| DML  | 데이터 조작어   | `INSERT`, `UPDATE`, `DELETE`, `MERGE`           | 행 데이터 변경                      |
| DQL  | 데이터 질의어   | `SELECT`                                        | 데이터 조회. 자료에 따라 DML에 포함 |
| DCL  | 데이터 제어어   | `GRANT`, `REVOKE`                               | 권한 부여·회수                      |
| TCL  | 트랜잭션 제어어 | `COMMIT`, `ROLLBACK`, `SAVEPOINT`               | 변경 확정·취소                      |

```sql
CREATE TABLE APP_USER.EXAMPLE (ID NUMBER);      -- DDL
INSERT INTO APP_USER.EXAMPLE VALUES (1);         -- DML
SELECT * FROM APP_USER.EXAMPLE;                 -- DQL
GRANT SELECT ON APP_USER.EXAMPLE TO TEST_USER;   -- DCL
COMMIT;                                        -- TCL
```

**트랜잭션 주의:** Oracle의 일반적인 DDL에는 암묵적 COMMIT이 따른다. `TRUNCATE`로 비운 데이터를 보통의 `ROLLBACK`으로 되돌릴 수 없다. 일반적인 DML은 COMMIT 전 ROLLBACK할 수 있다. `GRANT`/`REVOKE`는 통상 DCL로 외우지만 Oracle의 SQL 명령 분류 및 트랜잭션 동작에서는 DDL 관련 성격을 갖는다.

## 2. 계정, 스키마, 테이블스페이스는 왜 다를까?

예를 들어:

```text
Oracle PDB: XEPDB1
├─ 사용자 / 스키마: APP_USER
│  ├─ APP_USER.EMPLOYEE  ── 저장 위치 ──> USERS 테이블스페이스
│  └─ APP_USER.ORDERS    ── 저장 위치 ──> DATA_TBS 테이블스페이스
├─ 사용자 / 스키마: TEST_USER
│  └─ TEST_USER.NOTES    ── 저장 위치 ──> USERS 테이블스페이스
└─ 테이블스페이스: SYSTEM, SYSAUX, USERS, TEMP 등
```

- **스키마**는 *누가 소유하느냐*의 문제다.
- **테이블스페이스**는 *어디에 저장하느냐*의 문제다.
- 여러 스키마가 같은 `USERS`를 쓸 수 있고, 하나의 스키마가 여러 테이블스페이스에 객체를 둘 수도 있다.
- 데이터파일(`.dbf` 등)은 테이블스페이스와 연결되는 **물리적 파일**이다. 테이블스페이스는 논리적 저장 단위다.
- `SYSTEM` 사용자/스키마와 `SYSTEM` 테이블스페이스는 **이름이 같지만 다른 것**이다. SYSTEM 계정의 기본 테이블스페이스는 보통 SYSTEM이고, 일반 개발용 테이블은 별도 계정과 USERS 등 업무용 테이블스페이스에 두는 편이 좋다.

### 기본 테이블스페이스와 사용 한도

```sql
-- 권한 있는 관리자 계정에서 실행
ALTER USER APP_USER DEFAULT TABLESPACE USERS;
ALTER USER APP_USER QUOTA 100M ON USERS;
```

첫 문장은 **기본 목적지**, 둘째 문장은 **공간을 할당받을 수 있는 한도**다. `DEFAULT TABLESPACE`를 바꿔도 **기존 테이블은 자동 이동하지 않는다**.

```sql
-- APP_USER 계정에서 실행 (DATA_TBS에 대한 QUOTA도 필요)
CREATE TABLE ORDERS (
    ORDER_ID NUMBER PRIMARY KEY
) TABLESPACE DATA_TBS;
```

## 3. 계정을 생성하면 자기 스키마에 CREATE TABLE이 자동 허용되나?

**아니다.** 계정/스키마가 생기는 것과 시스템 권한을 갖는 것은 별개다.

```sql
-- SYSTEM 등 권한 있는 관리자 계정
CREATE USER TEST_USER
IDENTIFIED BY "ChangeMe_123!"
DEFAULT TABLESPACE USERS
TEMPORARY TABLESPACE TEMP
QUOTA 100M ON USERS;

GRANT CREATE SESSION, CREATE TABLE TO TEST_USER;
```

| 항목                       | 하는 일                        |
| -------------------------- | ------------------------------ |
| `CREATE USER`              | 사용자 및 스키마를 생성        |
| `CREATE SESSION`           | DB에 로그인 허용               |
| `CREATE TABLE`             | 자기 스키마에 테이블 생성 허용 |
| `DEFAULT TABLESPACE USERS` | 기본 저장 위치 설정            |
| `QUOTA 100M ON USERS`      | USERS 공간 할당 한도 설정      |

자기 **소유 테이블**의 `SELECT`, `INSERT`, `UPDATE`, `DELETE`, 일반적인 `ALTER`, `DROP`에는 별도 객체 권한을 다시 GRANT할 필요가 없다. 단, 새 객체를 **생성**하는 데는 해당 시스템 권한이 필요하고 저장 공간 한도 및 다른 객체에 대한 추가 권한이 영향을 줄 수 있다.

## 4. 다른 스키마의 특정 테이블에 접근 권한 주기

조건: `APP_USER`는 `EMPLOYEE` 소유자, `TEST_USER`는 접근할 사용자.

```sql
-- APP_USER(소유자)에서 실행
GRANT SELECT ON APP_USER.EMPLOYEE TO TEST_USER;

GRANT INSERT, UPDATE, DELETE
ON APP_USER.EMPLOYEE TO TEST_USER;
```

```sql
-- TEST_USER에서 실행
SELECT * FROM APP_USER.EMPLOYEE;

UPDATE APP_USER.EMPLOYEE
SET SALARY = 6000
WHERE EMP_ID = 8;

COMMIT;
```

`APP_USER.EMPLOYEE`에서 앞은 **스키마명**, 뒤는 **테이블명**이다. `TEST_USER`가 권한을 받아도 테이블 소유자는 여전히 `APP_USER`다.

### DML 권한과 DDL 관련 객체 권한을 같이 부여하기

```sql
-- APP_USER에서 실행
GRANT SELECT, INSERT, UPDATE, DELETE, ALTER, INDEX
ON APP_USER.EMPLOYEE TO TEST_USER;
```

- `ALTER`: 해당 **기존 테이블**의 구조 변경(일부 작업은 별도 권한·제약을 요구할 수 있음).
- `INDEX`: 해당 테이블에 대한 인덱스 생성 관련 객체 권한. 실제 생성에는 인덱스 소유자, 스키마 및 저장 공간의 추가 조건이 있을 수 있음.
- 위 명령은 **EMPLOYEE 테이블 하나**에만 적용된다.

```sql
-- TEST_USER에서 실행: ALTER 객체 권한을 받았다면
ALTER TABLE APP_USER.EMPLOYEE
ADD EMAIL VARCHAR2(100);
```

> **주의:** `GRANT ALTER ON A.EMPLOYEE TO B`는 가능하지만 `GRANT DROP ON A.EMPLOYEE TO B` 및 `GRANT TRUNCATE ON A.EMPLOYEE TO B`는 일반적인 Oracle 테이블 객체 권한으로 지원되지 않는다.

## 5. 객체 단위, 전체 DB 수준, 스키마 단위의 범위 차이

### 5-1. 테이블 하나에만 적용 (객체 권한)

```sql
GRANT SELECT ON APP_USER.EMPLOYEE TO TEST_USER;
```

`APP_USER.ORDERS`까지 읽을 수 있게 되지는 않는다. 다른 테이블은 별도 GRANT가 필요하다.

```sql
GRANT SELECT ON APP_USER.ORDERS TO TEST_USER;
GRANT SELECT ON APP_USER.DEPARTMENT TO TEST_USER;
```

### 5-2. 많은 스키마에 적용하는 ANY 시스템 권한 (강력함)

```sql
-- 관리자에서 실행: 연습 목적으로 무분별하게 사용하지 말 것
GRANT SELECT ANY TABLE TO TEST_USER;
GRANT ALTER ANY TABLE TO TEST_USER;
GRANT CREATE ANY TABLE TO TEST_USER;
GRANT DROP ANY TABLE TO TEST_USER;
```

- `SELECT ANY TABLE`: 대부분의 스키마에 있는 테이블 조회
- `ALTER ANY TABLE`: 대부분의 스키마 테이블 변경
- `CREATE ANY TABLE`: 다른 스키마에 테이블 생성
- `DROP ANY TABLE`: 다른 스키마의 테이블 DROP 또는 TRUNCATE

**보호 예외:** `SYS`, `AUDSYS` 및 데이터 딕셔너리 등에는 별도 보호 규칙이 있다. `ANY`라고 해서 예외 없이 모든 내부 객체를 조작하는 것은 아니다.

**CREATE ANY TABLE과 QUOTA 예시:**

```sql
-- 관리자: TEST_USER에게 다른 스키마 생성 권한 부여
GRANT CREATE ANY TABLE TO TEST_USER;

-- 관리자: 실제 테이블 소유자인 APP_USER의 공간 한도 확보
ALTER USER APP_USER QUOTA 100M ON USERS;

-- TEST_USER에서 실행
CREATE TABLE APP_USER.DEMO_TABLE (ID NUMBER);
```

이때 생성하는 사람은 TEST_USER지만, **테이블 소유자는 APP_USER**다. 테이블이 저장되는 테이블스페이스의 **소유자 측 QUOTA**가 필요하다(또는 적절한 면제 권한).

### 5-3. 스키마 A 전체에만 권한을 주고 싶다면?

- **Oracle 19c / 21c 등:** 일반적으로 기존 테이블마다 객체 권한을 따로 부여하거나, 관리자 스크립트로 여러 GRANT를 실행한다. `GRANT SELECT ON APP_USER.* TO TEST_USER`는 지원되는 문법이 아니다.
- **Oracle 23ai 계열 이후 지원 기능:** 스키마 수준 권한을 사용할 수 있다. 예:

```sql
GRANT SELECT ANY TABLE ON SCHEMA APP_USER TO TEST_USER;
```

이 예시는 해당 기능을 지원하는 Oracle 버전에서 **APP_USER 스키마 범위로 제한**하며, 새로 만들어지는 테이블에도 적용되는 방식이다. 버전과 부여 주체의 권한 요건을 확인해야 한다. Oracle XE의 버전을 확인한 뒤 사용하자.

### 범위 요약

| 구문                                                     | 적용 범위                                       |
| -------------------------------------------------------- | ----------------------------------------------- |
| `GRANT SELECT ON APP_USER.EMPLOYEE TO TEST_USER`         | EMPLOYEE 한 개                                  |
| `GRANT SELECT ANY TABLE TO TEST_USER`                    | 대부분의 다른 스키마 테이블                     |
| `GRANT SELECT ANY TABLE ON SCHEMA APP_USER TO TEST_USER` | 지원 버전에서 APP_USER 스키마에 속하는 테이블들 |

## 6. DDL도 테이블 단위로 권한을 줄 수 있나?

**부분적으로 가능하다.**

| 작업                          | 특정 테이블만 지정해서 부여?   | 예시 또는 대안                                  |
| ----------------------------- | ------------------------------ | ----------------------------------------------- |
| `SELECT`                      | 가능                           | `GRANT SELECT ON A.T TO B`                      |
| `INSERT`, `UPDATE`, `DELETE`  | 가능                           | `GRANT UPDATE ON A.T TO B`                      |
| `ALTER TABLE`                 | 가능                           | `GRANT ALTER ON A.T TO B`                       |
| 그 테이블에 `CREATE INDEX`    | 가능(관련 조건 확인)           | `GRANT INDEX ON A.T TO B`                       |
| 그 테이블만 `DROP TABLE`      | 일반 객체 권한으로 불가        | 소유자 또는 강력한 `DROP ANY TABLE` 권한        |
| 그 테이블만 `TRUNCATE`        | 일반 객체 권한으로 불가        | 소유자 또는 강력한 `DROP ANY TABLE` 권한        |
| A 스키마에 새 테이블 `CREATE` | 기존 테이블 객체 권한으로 불가 | `CREATE ANY TABLE` 또는 지원 버전의 스키마 권한 |

**`DELETE`와 `TRUNCATE`는 다르다.** `DELETE`는 DML이고 조건을 걸 수 있으며 일반적으로 트랜잭션 롤백 대상이다. `TRUNCATE`는 DDL이고 전체 행을 신속하게 제거하며 통상 `ROLLBACK`할 수 없다.

## 7. 권한은 누가 GRANT할 수 있나?

- **자기가 소유한 테이블의 객체 권한**: 소유자가 직접 GRANT할 수 있다.
- **다른 소유자의 테이블 권한을 재부여**: 적절한 `WITH GRANT OPTION` 또는 관리자 권한이 필요하다.
- **CREATE TABLE 같은 시스템 권한**: 해당 권한을 부여할 수 있는 관리자 권한이 필요하다.
- **관리자 SYSTEM**이라고 해도 무조건 모든 보호 객체에 제약 없이 접근하는 것은 아니다.

```sql
-- 소유자가 다른 사용자에게 권한을 다시 줄 수 있도록 허용하는 사례
GRANT SELECT ON APP_USER.EMPLOYEE
TO TEST_USER WITH GRANT OPTION;
```

`WITH GRANT OPTION`은 권한 재부여를 가능하게 하므로 꼭 필요한 경우에만 사용한다. 시스템 권한을 재부여하는 `WITH ADMIN OPTION`과 구별하자.

### 권한 회수

```sql
-- APP_USER에서 실행
REVOKE UPDATE ON APP_USER.EMPLOYEE FROM TEST_USER;
```

직접 권한을 회수해도 다른 역할이나 별도 경로로 같은 권한을 갖고 있으면 계속 사용할 수 있을 수 있다.

## 8. 자주 발생하는 오류

### ORA-01031: insufficient privileges

작업 권한이 부족한 경우다. 예: `CREATE TABLE`이 없는 계정에서 테이블 생성 시도.

```sql
-- 관리자에서 실행
GRANT CREATE TABLE TO APP_USER;
```

### ORA-01950: no privileges on tablespace 'USERS'

`USERS`에서 객체 저장에 필요한 공간 할당 권한/QUOTA가 없는 경우다.

```sql
-- 관리자에서 실행
ALTER USER APP_USER QUOTA 100M ON USERS;
```

`GRANT CREATE TABLE`만 반복해도 QUOTA 문제가 해결되는 건 아니다. **실제 객체 소유자**의 공간 한도를 확인한다.

### ORA-00942: table or view does not exist

테이블이 없거나, 이름/스키마가 다르거나, 접근 권한이 없는 경우에도 나타날 수 있다.

```sql
-- 스키마 접두어를 명시
SELECT * FROM APP_USER.EMPLOYEE;
```

필요하다면 소유자에게 SELECT 객체 권한을 요청한다.

## 9. 현재 계정·권한·저장 위치 조회 SQL 모음

### 지금 누구로, 어느 PDB에 접속했나?

```sql
SELECT
    USER AS LOGIN_USER,
    SYS_CONTEXT('USERENV', 'CON_NAME') AS CONTAINER_NAME
FROM DUAL;
```

### 기본 테이블스페이스

```sql
-- 현재 계정
SELECT USERNAME, DEFAULT_TABLESPACE, TEMPORARY_TABLESPACE
FROM USER_USERS;

-- 관리자: 전체 계정
SELECT USERNAME, DEFAULT_TABLESPACE, ORACLE_MAINTAINED
FROM DBA_USERS
ORDER BY USERNAME;
```

### 공간 사용 한도

```sql
-- 현재 계정
SELECT TABLESPACE_NAME, BYTES, MAX_BYTES
FROM USER_TS_QUOTAS;

-- 관리자: APP_USER
SELECT USERNAME, TABLESPACE_NAME, BYTES, MAX_BYTES
FROM DBA_TS_QUOTAS
WHERE USERNAME = 'APP_USER';
```

`MAX_BYTES = -1`은 해당 QUOTA 항목에서 무제한을 뜻한다. 뷰에 행이 없으면 일반적인 명시적 QUOTA가 없을 수 있으며, `UNLIMITED TABLESPACE` 시스템 권한 등의 별도 가능성도 확인해야 한다.

### 실제 테이블 소유자와 저장 위치

```sql
-- 관리자
SELECT OWNER, TABLE_NAME, TABLESPACE_NAME
FROM DBA_TABLES
WHERE TABLE_NAME = 'EMPLOYEE';
```

### 내 시스템 권한과 현재 세션 권한

```sql
SELECT PRIVILEGE FROM USER_SYS_PRIVS;

SELECT PRIVILEGE FROM SESSION_PRIVS
WHERE PRIVILEGE LIKE '%TABLE%';
```

`USER_SYS_PRIVS`는 사용자에게 직접 부여된 시스템 권한을 확인할 때 유용하고, `SESSION_PRIVS`는 역할 등을 통해 현재 세션에 활성화된 시스템 권한도 확인할 수 있다.

### 관리자에서 객체 권한 조회

```sql
SELECT OWNER, TABLE_NAME, GRANTEE, PRIVILEGE
FROM DBA_TAB_PRIVS
WHERE OWNER = 'APP_USER'
ORDER BY TABLE_NAME, GRANTEE, PRIVILEGE;
```

### DB 버전 확인

```sql
SELECT BANNER FROM V$VERSION;
```

해당 뷰의 조회 권한이 없다면 관리자 계정에서 실행하거나, DBeaver의 연결 정보에서 Oracle 버전을 확인한다.

## 10. DBeaver에서 SYSTEM 스키마가 안 보이는 경우

1. 왼쪽 **Database Navigator / Connections**에서 실제 연결이 `XEPDB1`인지 확인한다.
2. SQL Editor에서 `SELECT USER FROM DUAL;`로 **접속 사용자**가 SYSTEM인지 확인한다.
3. 스키마 목록의 검색·필터, **시스템 객체 숨김**, **연결된 사용자 스키마만 표시** 옵션을 확인한다.
4. 새로고침하거나 재연결한다.
5. 관리자라면 `SELECT USERNAME FROM DBA_USERS WHERE USERNAME='SYSTEM';`로 **계정 존재**를 별도로 확인한다.

> **왼쪽 탐색기에 SYSTEM 스키마가 표시되지 않는 것과 SYSTEM 계정의 관리자 권한을 사용할 수 있는 것은 별개다.** 표시 문제를 먼저 고치지 않아도 SYSTEM으로 접속된 SQL Editor에서 권한 설정을 할 수 있다.

## 11. 한 번에 따라 해 보는 연습 (개인 실습 DB에서만)

**전제:** `APP_USER`, `TEST_USER`가 이미 있고, `APP_USER.EMPLOYEE`가 존재한다고 가정한다. 실행 계정을 꼭 구분한다.

```sql
-- [1] SYSTEM 등 관리자 계정: APP_USER가 자기 테이블을 만들 수 있도록
GRANT CREATE SESSION, CREATE TABLE TO APP_USER;
ALTER USER APP_USER DEFAULT TABLESPACE USERS;
ALTER USER APP_USER QUOTA 100M ON USERS;

-- [2] APP_USER 계정: TEST_USER에게 특정 테이블 읽기만 허용
GRANT SELECT ON APP_USER.EMPLOYEE TO TEST_USER;

-- [3] TEST_USER 계정: 조회
SELECT * FROM APP_USER.EMPLOYEE;

-- [4] APP_USER 계정: 수정 권한 추가
GRANT UPDATE ON APP_USER.EMPLOYEE TO TEST_USER;

-- [5] TEST_USER 계정: 필요할 때 수정 후 COMMIT
UPDATE APP_USER.EMPLOYEE
SET SALARY = SALARY + 100
WHERE EMP_ID = 8;
ROLLBACK;  -- 수정 취소 연습

-- [6] APP_USER 계정: UPDATE 권한 회수
REVOKE UPDATE ON APP_USER.EMPLOYEE FROM TEST_USER;
```

### 꼭 기억할 핵심 질문 5개

1. **자기 스키마면 무조건 CREATE TABLE 가능?** → 아니오. 시스템 권한과 QUOTA를 구분한다.
2. **`USERS`는 스키마?** → 아니오. 테이블스페이스 이름이다.
3. **`GRANT SELECT ON APP_USER.EMPLOYEE`는 APP_USER의 전체 테이블에 적용?** → 아니오. EMPLOYEE 한 개다.
4. **`GRANT ALTER ON ...`은 가능하지만 `GRANT DROP ON ...`은?** → 일반적인 테이블 객체 권한으로 DROP은 없다.
5. **A 스키마 테이블을 B가 생성하면 누구의 QUOTA?** → 실제 소유자인 A가 저장 공간 한도를 확보해야 한다.
